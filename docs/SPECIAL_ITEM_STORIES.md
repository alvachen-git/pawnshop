# 特殊物品背景故事档案

版本：设计稿 1.0 · 2026-09-07。依据：负责人本次确认的《泣血铜镜故事定稿与特殊物品背景档案》方案。

本档案面向编剧、策划与开发者，包含作者真相和结局剧透，不是玩家可直接阅读的游戏内图鉴。最初设计轮仅交付文档。2026-09-08已完成第一章本地代码，当前进度与验证见[铜镜第一章说明](MIRROR_CHAPTER.md)；完整结局与未来物品联动仍属设计。

## 1. 如何阅读与维护

所有条目使用以下状态，不以“文档已定稿”代替“游戏已实现”：

| 状态 | 含义 | 使用要求 |
| --- | --- | --- |
| 当前已实现 | 在注明的本地内容版本或历史版本中可以核实的行为 | 给出运行定义、内容或服务依据；本地可运行不等于已远程发布 |
| 本次确定的设计 | 负责人已确认的故事与玩法方向，尚未接入运行 | 可以据此继续写作；后续代码、数值与排程实施另行安排 |
| 未来候选 | 供后续评估的故事或联动方向 | 不当作既定真相，不提前加入对白、存档标记或实现任务 |

同一物品可以同时包含三种状态，必须逐节区分。新决定只覆盖其明确涉及的设计范围，不改写历史运行定义。历史文档保留阶段背景；不得用新版作者设定推断旧存档中的客人身份或证据。

玩家文字遵循 [玩家文案规范](PLAYER_COPY_GUIDE.md)。作者文档可以写清死亡、次数、触发条件和未实现内容；玩家正文只展示当时有来源的信息和清楚的操作。未来新物品不因同属鬼货就默认共享人物、禁忌或能力。

## 3. 单件物品档案模板

新增档案时沿用以下结构。文档中的线索编号和分支编号仅供写作追踪，不能直接假定为现有运行标识。

| 部分 | 必填内容 |
| --- | --- |
| 身份与流转 | 名称、已有物品标识、原主、重要外观、年代相对顺序、每次流转原因、当前去向；区分作者真相与已知来历 |
| 作者真相 | 完整因果链、各人物知情时间、动机、不可擅改事实；哪些问题刻意留给其他故事，不能用“神秘”代替本篇答案 |
| 能力与禁忌 | 能力来源、可回答与不可回答的问题、使用条件、收益、代价、预警、异常、失效条件 |
| 玩家调查 | 每条线索的载体、记录者或见证人、取得条件、能证明什么、不能证明什么、误判如何纠正、错过后的调查入口 |
| 剧情分支 | 节点前置、玩家实际行动、结果、退出方式、持有或售出差异、最终结局与未决状态 |
| 物品联动 | 相关人物／地点／交易／物件、依据、联动条件、可见结果、缺件路径、是否影响能力或结局、设计状态 |
| 实现状态 | 当前本地或历史版本依据、新设计差异、未来候选、文档修订日期；未实施的数值与系统不能写成当前功能 |

调查设计应将“看见异常”“产生怀疑”“证实事实”分开。一个作者知道的事实，必须有玩家可接触的来源才能进入其记录或选项。影像、传闻和当事人的解释都不是自动成立的证据。

## 4. 联动登记规则

联动分为三类：

1. **共同人物或旧事**：两件物品从不同角度留下同一事件的证据，不要求共同持有。
2. **共同持有时的反应**：特定物品同时在场产生异象，必须解释它们为何相关；持有本身不自动证明完整背景。
3. **结局影响其他物品**：一件物品的故事处理结果改变另一件物品的对白、线索或分支。必要主线应有独立入口，不能随意制造缺件死局。

每项登记填写：联动编号、双方物品、关系依据、状态、触发条件、玩家所见、能得出的结论、缺少任一物品的路径、对收益与结局的影响。涉及新物品时先补其档案，不用一句“同属阴物”解释反应。

## 5. 文档验收与后续维护

- 作者能沿着时间线说明“能力为何产生、为何此时触发、人物为什么这么做”。
- 每项揭晓能回指线索来源，未获得资料不会在结尾自动补齐。
- 能力有经营价值，也有明确边界；普通品相检查和自由报价仍成立。
- 拒收、售出、不使用、主动收手与错过来客都有路径；只有触发并确认的结果才能写入收尾。
- 单件故事能独立得到局部或完整答案，联动不会取代本篇必要解释。
- 当前实现、已确定设计和候选分别标注；新文档没有修改旧存档或授予开发、发布权限。

后续实际开发时，再为已选章节补具体交易配置、调查耗时、存档设计和工程验收。本次档案中的完整故事结局不表示七夜版已经实现，也不承诺第八夜之后的排程。
